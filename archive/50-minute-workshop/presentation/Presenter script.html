How to use this script

Read the SAY and TRANSITION blocks aloud. Everything in DO, COMMAND, EXPECT and CHECK is a stage direction, not something to read to the audience. Conditional SAY blocks replace the normal wording; do not read every branch. Read success wording only after the EXPECT check is satisfied. If it is not, use the relevant conditional wording and the recorded fallback instead. Waiting commentary is optional: skip it when the result is already available. Use the HTML or Markdown version when copying commands. The PDF is for reading and printing; its visual line wraps can introduce unwanted breaks when copied.

The clock starts when you begin slide 1. Slide 15 starts at minute 50. The five hidden appendix slides are answers to questions, not additional presentation material. The script assumes a mixed business/technical customer audience.

The recorded evidence is from 8 November 2026: baseline version 2 passed seven of nine synthetic cases; corrected version 4 passed nine. These are recorded facts, not a promise that a fresh model response will be identical. No live Azure calls or deployments are required merely to read this script.

Most demonstrations begin with a question and end with an impressive response. That is useful, but it leaves several important questions unanswered.

Where did the facts come from? Did the agent use the right tool? If we change its instructions tomorrow, how do we know we have not broken something that worked today? And when a user asks a question we did not anticipate, how does that observation become a better next version?

Slide 04 - One continuous system: inner and outer loop

TIME

04:00-07:00. Allow time for the audience to inspect the diagram.

DO

Trace the left-hand loop, the upper forward bridge, the right-hand loop and finally the lower return bridge. Do not read every box.

SAY

This is the mental model for the rest of the session. There are two loops and, just as importantly, two bridges between them.

The inner loop, on the left, is the developer's learning cycle. We define the behaviour, connect the tools, run the agent, inspect what happened, evaluate it against expectations, and improve the candidate.

The important word is candidate. A developer saying "this looks better" is not yet a release decision.

Look at the upper bridge. What moves forward is not simply a copied prompt. It is a versioned candidate with evidence: which configuration was used, which cases were evaluated, what passed, what failed, and what boundaries were checked. That is what makes a change reviewable.

The outer loop, on the right, is the repeatable release and operating process. It applies the gates, puts an identified version into service, and watches what that version does when it receives requests.

Now follow the lower arrow back to development. This is the connection that is often missing. An operational observation is reviewed, the expected behaviour is defined, and a new test becomes part of what the next candidate must prove.

That human review is important. A response found in a trace is not automatically the right answer, and a model-generated finding is not automatically the right fix.

This picture is the broader reference architecture. We will not demonstrate every capability on it. Our compact implementation uses local development and a hosted demo target. It is not a separately isolated customer production environment.

What we will demonstrate is both evidence bridges: candidate to release, and observed behaviour back to a test. Keep those two arrows in mind. They connect everything that follows.

There are two uses of Copilot in this story, and I want to distinguish them.

First, GitHub Copilot helps the developer write and understand the application code, tests and workflow. That is the development experience.

Second, the GitHub Copilot SDK is the harness inside this particular application. It manages the agent interaction with the model and the tools we have exposed. It is not the same thing as handing our customers an unrestricted coding assistant.

In this implementation, the customer-facing runtime has three allowlisted, read-only business tools. It is not given general shell or filesystem access.

Foundry then hosts that application and provides the endpoint and the surrounding lifecycle capabilities. The model also runs through Foundry, authenticated with Microsoft Entra. We have not embedded a GitHub token in the business agent.

The graphic shows that hosted agents are not limited to this one framework. We chose the Copilot SDK because it makes our GitHub-to-Foundry story concrete. The framework choice does not remove our responsibility for the tool logic, permissions, evaluation coverage or release policy.

The managed Foundry Toolbox and API Management are useful extension points, but they are not configured in this sample. Our three tools are packaged with the agent. I will distinguish what we actually run from the broader platform architecture.
